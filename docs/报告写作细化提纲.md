# 第 1 章 需求分析

## 1.1 系统需求

### 1.1 开头：业务背景（写 1 段）
- 传统实验室设备管理痛点：纸质/Excel 台账 → 状态更新滞后、借还难追溯、审批不规范、权限失控。
- 本系统目标：把"设备入库→借用申请→审批→归还→统计"全流程搬到 Web，实现无纸化、规范化、数据化。

### 1.1.1 角色需求（按三角色写）
代码锚点：`backend/app/__init__.py → _seed_data()`

| 角色 | 角色码 | 能做什么 |
|------|--------|---------|
| 普通用户 | NORMAL_USER | 浏览设备、申请借用、查本人记录 |
| 实验室管理员 | LAB_ADMIN | 设备增删改、审批借用、确认归还、查全部记录、看统计 |
| 超级管理员 | SUPER_ADMIN | 全部权限 + 用户管理 + 角色分配 + 审计日志 |

⭐出彩点：权限不是写死在角色里，而是"角色→权限码"关联（18 个权限码），改权限不用改代码。

### 1.1.2 功能模块（5 大模块，对应图 1-1）
代码锚点：8 个蓝图

| 模块 | 对应代码 | 核心功能 |
|------|---------|---------|
| 用户与权限 | `api/auth.py` `api/user.py` `api/roles.py` | 注册/登录/改密/信息管理/角色权限 |
| 设备基础 | `api/device.py` `api/category.py` | 分类/入库/编辑/软删除/状态维护/多条件查询 |
| 设备借用 | `api/borrow.py` | 申请/审批/归还申请/确认归还 |

## 1.2 安全需求 ⭐（本节是评分核心，六维度逐一写）
代码锚点：见下表逐项

| 维度 | 需求描述 | 真实实现锚点 | ⭐亮点 |
|------|---------|-------------|--------|
| ①身份认证 | 用户名+密码+验证码；密码复杂度；失败锁定；JWT 有效期 | `api/auth.py` `utils/validators.py→check_password_complexity` | 验证码存 Redis 60s；失败 3 次起渐进提示，5 次锁 10 分钟 |
| ②访问控制 | RBAC；后端接口鉴权；前端菜单动态渲染；普通用户只看自己记录 | `utils/auth_helper.py→require_permission` `router/index.js` | 基于**权限码**而非角色名鉴权；行级隔离（record:self vs record:all）|
| ③传输安全 | Nginx HTTPS；HTTP 自动跳 443 | `deploy/nginx/lab.conf` | TLS1.2/1.3 + HSTS 头 |
| ④应用安全 | 防 SQL注入/XSS/CSRF/目录遍历 | `utils/validators.py→sanitize_input,is_safe_path`；ORM 参数化 | XSS 用 html.escape；目录遍历有 is_safe_path 校验 |
| ⑤数据安全 | 密码不明文（SM3+盐）；手机号 SM4 加密+脱敏；审计日志 | `utils/crypto.py` | **国密 SM3/SM4**，可一键切 openssl 兜底 |
| ⑥网络安全 | 防火墙只开 80/443；DB/Redis 不暴露公网 | `deploy/部署对接清单.md → ufw` | 最小暴露面；Gunicorn 仅听 127.0.0.1 |

⭐本节收尾点题：本系统不是"加了登录的 CRUD"，而是从身份/访问/传输/应用/数据/网络六个维度做了纵深防御（Defense in Depth）。

## 2.1 系统设计

### 2.1.3 业务流程设计（图 2-3）⭐
代码锚点：`backend/app/api/borrow.py`
- 📌 图 2-3 借用状态机（按真实代码画，注意是"审批通过即借出"）：
```
[申请] PENDING ──管理员审批通过──> BORROWED ──用户申请归还──> RETURN_PENDING ──管理员确认──> RETURNED
           └──────审批驳回──────> REJECTED
```

### 2.1.5 数据表设计（ER 图 + 核心表）

## 2.2 安全设计（把 1.2 的"需求"展开成"怎么实现"）

### 2.2.1 身份认证
代码锚点：`utils/crypto.py→hash_password/verify_password` `api/auth.py`
- 注册：密码复杂度校验 → SM3 加随机盐哈希入库（绝不存明文）。
- 登录：图片验证码(Redis 60s) → 校验密码 → 失败计数(5次锁10分钟，3次起渐进提示) → 成功签发 JWT(2h)。
- ⭐贴 hash_password 的加盐流程；说明 SM3 是国密哈希。

### 2.2.2 访问控制（权限管理）⭐
代码锚点：`utils/auth_helper.py→require_permission` `middlewares/auth_middleware.py`
- RBAC 三层：用户 ←user_roles→ 角色 ←role_permissions→ 权限。
- 中间件 before_request 解 JWT，把当前用户权限集放进 g。
- `@require_permission("xxx:yyy")` 装饰器逐接口校验，401(未登录)/403(无权限)分离。
- 前端：路由 meta.perm + 动态侧边栏按权限过滤。
- ⭐行级数据隔离：`record:self` 只看自己，`record:all` 看全部——同一接口不同权限返回不同数据范围。

### 2.2.3 传输保护（安全协议）
代码锚点：`deploy/nginx/lab.conf` `deploy/gen_cert.sh`
- Nginx 配 HTTPS（自签证书），80 端口 301 跳 443。
- TLS 只留 1.2/1.3；加 HSTS、X-Frame-Options、nosniff 等安全响应头。
- ⭐后端 ProxyFix 信任 Nginx 透传的真实 IP，审计日志才不会全记成 127.0.0.1。

### 2.2.4 Web 安全防护
代码锚点：`utils/validators.py`
- SQL 注入：全程 SQLAlchemy ORM 参数化，无字符串拼 SQL。
- XSS：`sanitize_input` 用 html.escape 转义。
- 目录遍历：`is_safe_path` 校验路径。
- CSRF：【待补——见文末待办】用自定义请求头校验（前端带 Token、后端验非简单请求）。

### 2.2.5 网络安全与入侵检测（两部分写）
- 实际部分：ufw 防火墙规则（仅 22/80/443），DB/Redis 仅监听本机。代码锚点 `deploy/部署对接清单.md`。
- 文字方案部分：Snort IDS 设计【待补 4 条规则】，例如检测端口扫描、SQL 注入特征、暴力登录、异常 User-Agent。

## 二、E-R 关系（文字版，画图依此）

```
users ──< user_roles >── roles ──< role_permissions >── permissions
  (多对多)                  (多对多)

device_categories ──< devices          (一分类对多设备)

users ──< borrow_records >── devices    (借用记录中间表关联人和设备)
  borrow_records.approver_id          → users.id  (审批人)
  borrow_records.return_confirmer_id  → users.id  (确认归还人)

operation_logs                          (独立日志表，只追加，不强外键)
```

实体与主要关系：
- **用户 ↔ 角色**：多对多，桥表 `user_roles`。一人可多角色（超管可同时是普通用户）。
- **角色 ↔ 权限**：多对多，桥表 `role_permissions`。
- **分类 → 设备**：一对多。设备只存 `category_id` 外键（消除传递依赖，符合 3NF）。
- **用户 / 设备 → 借用记录**：借用记录是核心业务表，外键关联申请人、设备、审批人、归还确认人。
- **操作日志**：独立，`username` 冗余存储免联表，只写不改。

## 三、第三范式核对要点（答辩可能问）

- 设备分类拆表：避免"电子测量仪器"在每台设备行重复，消除传递依赖。
- 日志表 `username` 冗余：是**有意为之**的反范式，为查询性能，日志只追加写，无更新异常风险。
- 借用记录的状态/时间字段都直接依赖主键 id，无部分依赖、无传递依赖。

## 四、借用状态机（开发借用模块时严格按此）

```
提交申请 → PENDING
  ├ 管理员通过 → APPROVED → 用户取走 → BORROWED
  │                                    ├ 超过预计归还日 → OVERDUE
  │                                    └ 用户申请归还 → RETURN_PENDING
  │                                                      └ 管理员确认 → RETURNED
  └ 管理员驳回 → REJECTED
```

⚠ 关键纪律：**审批通过**（改借用状态 + 改设备状态为借出）和**确认归还**（改借用状态 + 改设备状态为空闲）两步，必须在**同一数据库事务**内完成。这是本项目最容易出错的地方。
